# Наименование: префектуры и города Японии

Связано: [[CHANGE_PLAN]] · Версии и отчёты

Крейты и релизы HC-physics называются по префектурам Японии. Крейты — по префектурам, релизы — по городам префектуры ядра. Документ фиксирует, как имена соотносятся с ролями и почему выбран такой способ.

## Как называется что

| Крейт                  | Префектура | Роль                                                      |
| ---------------------- | ---------- | --------------------------------------------------------- |
| `hc-physics` (`core/`) | Сига       | база — библиотека: math, body, fluids, material, acoustic |
| `hc-physics-bevy`      | Коти       | адаптер для Bevy (самостоятельный слой)                   |
| `hc-physics-unity`     | Нара       | нативная библиотека для Unity (`cdylib`, C ABI; не начат) |
| `hc-physics-godot`     | Сага       | адаптер для Godot (на будущее, не решено)                 |

> [!tip] Иерархия Город внутри префектуры = «производный от базы». Релизы ядра называются городами Сиги, поэтому каждый релиз «живёт внутри» базы. Новая префектура = «самостоятельный слой» (адаптер, отдельный стенд).

### Где записывается кодовое имя

`Cargo.toml` не принимает кодовое имя в поле `version`, поэтому оно хранится отдельно:

toml

```toml
[package.metadata.hc]
codename = "otsu"
```

или в коде:

rust

```rust
pub const CODENAME: &str = "Otsu";
```

### Формат имён файлов

|Что|Шаблон|Пример|
|---|---|---|
|Версия|`<номер> <стадия> «<Город>»`|`0.75.5 alfa «Otsu»`|
|Архив|`hc-engine-<дд-мм-гг>-<номер>-<стадия>-<город>.zip`|`hc-engine-18-10-26-075-alfa-otsu.zip`|
|Отчёт|`hc-report-<дд-мм-гг>-<№ отчёта>-<версия>-<стадия>-<город>.md`|`hc-report-18-10-26-002-0.75.5-alfa-otsu.md`|

## Почему так, а не иначе (мотивировка)

Единой системы именования у проектов обычно нет — имена присваиваются «как придётся»: где-то это мифологические имена, где-то — описание того, что делает модуль, и оно устаревает, когда назначение меняется.

Здесь выбраны названия японских префектур и городов, потому что они:

- **индивидуальные и готовые** — не нужно придумывать, они существуют сами по себе, короткие и запоминающиеся;
- **нейтральные** — ничего не утверждают о коде, поэтому имя не устареет, когда крейт сменит назначение;
- **иерархичные** — отношение «город внутри префектуры» ложится на отношение «релиз внутри базы»;
- **последовательные с остальными проектами** — тот же подход, что и в других моих проектах.

## Правила

1. **Нейтральность.** Имя не должно иметь тяжёлой исторической окраски (Хиросима, Нагасаки, Фукусима и подобные).
2. **Одна префектура — один слой.** Новый слой получает новую префектуру, а не город.
3. **Город — только для релизов ядра.** Исключение — случай, когда у модуля внутри `core` появится собственный крейт: тогда его можно назвать городом Сиги, но вне пула релизов.
4. **Занятые имена не повторяются между проектами.** В другом проекте уже заняты Тоттори, Йонаго и Нагано; здесь они не используются.
5. **Порядок релизов не меняется.** Пул идёт по таблице, пропуски и перестановки не допускаются.

## Свободные слоты (не решено)

- Новый адаптер или стенд — следующая префектура, например Окаяма, Фукуока, Кагава (не зафиксировано).
- Когда пул городов Сиги закончится (после 13-го релиза) — вернуться к вопросу: перейти на пул другой префектуры или сменить схему (не решено).
